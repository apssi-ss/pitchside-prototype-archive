## Cross-route functional findings

| ID / severity      | Finding                                                                                                                                                                            | Risk / recommendation                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RF-01 / **High**   | "Save," "pay," "submit," "assign," and "send" labels frequently produce local state updates or success toasts only. See payment, SSB, coach, referee and organizer evidence above. | Users could mistake presentation for completed business transactions. Keep these flows clearly designated as prototype until server-backed outcomes and failure states exist. |
| RF-02 / **High**   | No route loaders or server functions are evidenced; route pages import demo constants directly.                                                                                    | Pages do not represent operational data, concurrent changes, validation failures, or role-scoped access. Define server use cases and contracts before replacing fixtures.     |
| RF-03 / **High**   | Consent, guardian approval and scout visibility are portrayed in UI but are not persisted or enforced by a trusted server.                                                         | Do not expose real child profiles through this screen until server-side authorization and consent enforcement are independently verified.                                     |
| RF-04 / **Medium** | Selected tournament category does not drive category-specific results; week/date is hard-coded; data is seeded at disparate dates.                                                 | Define authoritative competition/calendar semantics and acceptance cases with product owners.                                                                                 |
| RF-05 / **Medium** | The only discovered test checks that `/` matches a route; no route behavior, access, persistence, form validation, or role boundary tests were found.                              | Define critical workflow and security tests before enabling real data.                                                                                                        |

## Unverified items / owner questions

- Which screens and workflows are in the initial production release, and what are their acceptance criteria?
- Are demo identities and event records entirely synthetic and approved for continued use? Do not use real child records in the mock module.
- What is the approved payment provider and what constitutes payment success (provider callback, reconciliation, or another authoritative signal)?
- What are the required guardian verification method, consent purposes, retention/withdrawal rules, and child data visibility rules?
- Which tournament data is public, which is participant-only, and what is authoritative for scores/standings?
- Are dates and metrics meant as demonstrations, and should the current category/date discrepancies be treated as intentional prototype copy or product defects?
