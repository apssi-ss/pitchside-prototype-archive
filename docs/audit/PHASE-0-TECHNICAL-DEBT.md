## Confirmed strengths

- TypeScript strict mode and checks such as `noImplicitReturns`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes` are enabled: [tsconfig.json](../../tsconfig.json#L8-L33).
- Route paths are generated and statically typed; the generated file explicitly warns not to edit it by hand: [src/routeTree.gen.ts](../../src/routeTree.gen.ts#L1-L8).
- QueryClient is constructed per router instance to avoid sharing cache across SSR requests: [src/router.tsx](../../src/router.tsx#L4-L14).
- Shared shell and presentational kit reduce repeated layout/control code: [src/components/app-shell.tsx](../../src/components/app-shell.tsx#L148-L242), [src/components/kit.tsx](../../src/components/kit.tsx#L1-L224).
- Server error wrapper and CSRF middleware are present as infrastructure: [src/start.ts](../../src/start.ts#L1-L33), [src/server.ts](../../src/server.ts#L1-L64).

## Technical debt owner decisions

- Which package manager/runtime is authoritative? The repo contains `package-lock.json`, `bun.lock` and `bunfig.toml`, while README instructions use npm.
- Which owner is responsible for backend/service contracts and whether route loaders or server functions are the approved integration boundary?
- Which shared design-system and accessibility checks are required for every route?
- Which fixture data may be used, and how should prototype status be communicated to avoid users interpreting UI confirmations as actual writes?
